Information architecture

Where does “all projects” belong?

NoxConnect owns the organization-wide plumbing. Product services operate within a project, but some read-only views can aggregate work across projects. These models show three ways to make that scope visible.

1
Keep ownership and viewing separate“All projects” is a viewing filter, not a place where product configuration lives. Settings and mutations always resolve to one clear owner.

Scope first

The project is the persistent primary context. NoxConnect is explicitly organization-wide; choosing another product keeps the selected project. Cross-project reading is offered only where it makes sense.

Why it works

  • The active project is never ambiguous.
  • Product settings cannot accidentally affect another project.
  • NoxConnect can switch the project selector to “Organization”.

Constraint

  • “All projects” should be read-only.
  • It should appear only in Feed and portfolio-style views.
  • Create/edit actions require selecting one project first.

Product first

Users choose NoxFeed, Ticket, Spot, Cue, or Connect first. Each product then decides whether it needs a project selector or supports an all-project view.

Why it works

  • Strong, distinct product identity.

Risk

  • Each product can develop different scope behavior.
  • Users may forget which project receives an action.
  • NoxConnect feels like another product rather than the foundation.

Three work modes

The whole application is split into Organization admin, Project work, and Portfolio. This makes scope explicit but adds a new conceptual layer users must understand.

Why it works

  • Scope mistakes become very unlikely.
  • Organization administration has a clear home.
  • Portfolio views can grow independently.

Risk

  • Three modes are another navigation concept.
  • Users may not know whether a page is “Portfolio” or “Project work”.
  • Likely too much structure for the current suite size.

Recommended ownership map

This stays constant whichever navigation model is chosen.

AreaOwner scopeRule
NoxConnectOrganizationConnections, credentials, identities, repositories, project definitions, transport, delivery state, API access and maintenance.
NoxTicketOne projectFeatures, backlog, specs and workflow always belong to one project.
NoxFeedProject + aggregatePosts and delivery settings belong to one project; current activity may be viewed across all projects.
NoxSpotOne projectSites and reports belong to a project; environments live beneath a site.
NoxCueOne projectSources, events, health rules and reports belong to a project; environments live beneath a source.
Slack deliveryShared transportNoxConnect owns workspaces, credentials and delivery; each product owns the content and project-specific destination policy.
Practical rule: an aggregate page may compare or filter projects, but it cannot save routing, create a feature, configure a widget, change a health rule, or send a post until one project is selected.
