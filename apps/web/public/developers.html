Architecture

A capability-first API

Start by asking the platform what is available. Every capability is present; the catalog reports current blockers, required connections, access levels, and exact operations. Clients follow advertised operations instead of guessing routes.

↳

Credentials stay behind NoxConnect

GitHub, Slack, and customer credentials are never returned by discovery, setup, configuration, or health APIs. Private capability modules receive only the bounded data they need.

  1. 01DiscoverAsk NoxConnect which capabilities are available to this organization. The response lists what each capability can do and the exact operations clients may call.
  2. 02InspectCheck whether the chosen capability is enabled and healthy. Setup reports anything still needed, such as a GitHub or Slack connection.
  3. 03ConnectStart a provider connection through the API. A person opens the returned link and approves access in GitHub or Slack; the client never receives the provider credential.
  4. 04ConfigureRead the current settings and keep the returned revision. Send it back with a change so newer work cannot be overwritten accidentally.
  5. 05OperateCall only the operations advertised for the selected capability. Check the access and change-safety labels before every write or destructive action.

Quickstart

Discover your workspace

For a person or supervised local agent, use the NoxConnect CLI flow below. For unattended automation, create a scoped token under NoxConnect → API access while signed in as an organization admin, choose exactly one enabled project, copy it once, and keep it in the runtime's secret store.

Use the credential made for the caller

Browsers use an opaque HttpOnly session and CSRF proof. Automation uses a scoped nox_sk_… token. Ingestion uses a source key. Never extract a browser cookie or reuse a GitHub or Slack provider token.

terminal · discover capabilities
curl https://app.noxhere.com/api/v1/services \
  --header "Authorization: Bearer $NOXCONNECT_API_TOKEN"

CLI connection

Tell a supervised agent to use one NoxConnect login

The human runs noxconnect login, completes GitHub approval in the browser, and selects a project once. Every NoxConnect process for that operating-system user then shares the credential, including agents with different config directories. Concurrent login and token refresh are serialized so only one browser approval or refresh-token rotation occurs. Never paste the access token, refresh token, browser cookie, GitHub token, or Slack token into chat.

terminal · connect and select context
npm install --global noxconnect
noxconnect login
noxconnect use YOUR_ORGANIZATION/YOUR_PROJECT
noxconnect whoami

Supervised local agent

Use the shared CLI session. Login is once per computer user; use changes organization or project context without creating another credential. Logging out revokes the session for every local process sharing it.

Headless agent or CI

Do not automate the human login. Inject a project-bound nox_sk_… token from an approved secret manager and call the API directly.

Authentication

Separate credentials for people, automation, and ingestion

Browser session

GitHub OAuth establishes an opaque Secure, HttpOnly, SameSite=Lax NoxConnect session cookie. Unsafe requests also require the matching X-CSRF-Token. GitHub credentials stay encrypted in the private connectors service.

Native session

NoxConnect brokers GitHub device approval and gives the CLI and first-party apps a 15-minute nox_at_… access token plus a rotating nox_rt_… refresh token. Provider credentials remain encrypted in the private connectors service.

Automation token

Authorization: Bearer nox_sk_… carries one organization, one project, environment, expiry, and explicit service read/write scopes. Values are shown once, stored only as hashes, and can be rotated or revoked.

Operations advertise member, admin, native_session, native_refresh, public, or ingest_key authentication. Browser and native requests may omit X-Project-ID for organization-wide data or supply it to narrow results. Automation scopes retain the compatibility IDs noxfeed (Activity), noxspot (Feedback), and noxcue (Incidents), with :read or :write, plus services:read for discovery. Every automation token remains bound to one project.

A NoxConnect nox_sk_… automation token authenticates API calls. It is separate from secrets stored or shared through NoxKey, and separate from source keys used by public Incidents and Feedback ingestion.

A raw GitHub token is not a NoxConnect API credential. Unsupported bearer formats return unsupported_credential without being sent to GitHub.

Lifecycle and audit

Automation tokens expire within 1–365 days, are shown once, and expose only a prefix afterward. Create, rotate, and revoke actions are audited. Browser provider-token refresh occurs only on the server.

Feedback widget identity

Pass signed-in users explicitly

The Feedback widget cannot read a host website's login session, cookies, or signup database. The website owner must pass the current user's name and email after the widget has loaded and repeat the call when the signed-in account changes.

The install snippet is anonymous by default

Adding a Feedback site and pasting its one-line snippet does not expose user identity. Without the integration below, the widget still works and reporters enter their own details. The current widget JavaScript global remains NoxSpot for compatibility.

browser · site-specific embed
// The site-specific script auto-initializes the compatibility NoxSpot global.
// Run this after it loads and whenever the signed-in user changes.
NoxSpot.identify({
  name: currentUser.name,
  email: currentUser.email,
  // Set true only if your site already obtained consent:
  notifyOnResolution: true,
});

// Clear cached identity on sign-out.
NoxSpot.identify(null);
browser · manual initialization
NoxSpot.init({
  siteId: "your-site-id",
  getReporter: () => ({
    name: currentUser.name,
    email: currentUser.email,
  }),
});

Privacy boundary

The reporter email is not copied into GitHub. NoxConnect encrypts and retains it only when notifyOnResolution is true.

Consent boundary

Omit notifyOnResolution to leave the widget checkbox under the reporter's control. A host may set it to true only when it has already obtained permission for that transactional update.

Incidents SDK

Know when the product experience breaks

The Incidents capability turns a few meaningful app outcomes into immediate, actionable alerts and a completed-day product pulse. It detects and preserves evidence; it never retries a user action, changes application state, or tries to replace logs, traces, and observability. Its currently published compatibility package is @noxcue/sdk.

  1. 01Create a sourceIn NoxConnect, open Incidents and create one source for each app environment. Link it to a project when the organization has more than one project.
  2. 02Choose deliverySelect the Slack workspace and channels for daily statistics and immediate alerts. Optionally connect a GitHub repository for deduplicated incident issues.
  3. 03Create the right keyUse an origin-restricted nox_pub_… publishable key in browsers or mobile clients. Keep a nox_secret_… key in the server's secret store for trusted user and activity facts.
  4. 04Add outcome callsWrap critical user journeys such as sign-up, login, password reset, and email verification. Send registration and meaningful activity facts from the trusted server.
  5. 05Verify end to endRun noxcue.test() from the app. Setup becomes live only after the Incidents service stores the event and Slack confirms delivery.
terminal · install
npm install @noxcue/sdk

Available now as @noxcue/sdk 0.1.7 on npm. Install without a version to receive the latest compatible release.

Use a publishable key restricted to the exact production or staging origins. The wrapper returns the original result and rethrows the original application error unchanged.

Use a secret key on the server. The Incidents service hashes user identifiers, deduplicates facts, and computes daily totals, active users, stickiness, comparisons, and registered custom metrics centrally.

✓

The SDK adds the evidence

Every report includes occurrence time, source, environment, release, runtime, SDK version, duration, a safe URL, classification, and redacted error details. Delivery uses short timeouts, retries one transient failure with the same event ID, and never makes Incidents availability part of the app's success path.

Standard features

Sign up, log in, password reset, and email verification work without inventing event names. A user rejection is recorded separately from a system failure, so invalid credentials do not become incidents.

Custom features and metrics

Register every custom.* feature or activity name in NoxConnect first. Unknown names become one bounded configuration error instead of silently creating ungoverned telemetry.

Detection, not diagnosis theatre

Incidents groups equivalent failures under a readable fingerprint, keeps the original message and technical error, and provides possible causes and fixes for a developer to investigate. A later successful user action does not automatically close an incident.

Separate environments

Production, staging, preview, development, and test each have their own source and key. Collection, daily digests, and alerts can be enabled independently, preventing staging noise from reaching production channels.

Browser code can report feature outcomes and safe errors. Trusted user statistics and custom activity facts require the server entry point. Never ship a nox_secret_… key to a browser.

Safe configuration

Read, revise, then write

Configuration updates use optimistic concurrency. Read the document, retain its ETag, then include that value in If-Match. A stale client receives 412 instead of overwriting newer work.

terminal · compare-and-swap update
# 1. Read the current config and response ETag
curl -i https://app.noxhere.com/api/v1/services/noxfeed/config \
  -H "Authorization: Bearer $NOXCONNECT_ACCESS_TOKEN" \
  -H "X-Org: $NOX_ORG"

# 2. Patch only owned fields using that revision
curl -X PATCH https://app.noxhere.com/api/v1/services/noxfeed/config \
  -H "Authorization: Bearer $NOXCONNECT_ACCESS_TOKEN" \
  -H "X-Org: $NOX_ORG" \
  -H 'If-Match: "current-revision"' \
  -H "Content-Type: application/json" \
  --data '{"releaseNotesPrompt":"Keep release notes concise."}'

Project selection is request context, not Activity configuration. Omit X-Project-ID for organization-wide data or supply an active project ID to narrow a browser or native request.

Capability-scoped

NoxConnect, Planning, and Activity expose strict writable fields in their compatibility service-config responses.

Resource-scoped

Feedback sites and Incidents sources remain authoritative. Their compatibility service config is read-only and links to the correct child resources.

Errors

One predictable v1 envelope

json · error response
{
  "apiVersion": 1,
  "error": {
    "code": "revision_conflict",
    "message": "Settings changed concurrently; fetch config and retry",
    "details": { "currentRevision": "…" }
  }
}

All /api/v1/* errors, including authentication and organization failures raised before a handler runs, use this envelope. Compatibility routes under /api/* may still return { "error": "message" }.

401Missing or invalid authentication.
403The caller lacks required organization or admin access.
409The requested write conflicts with resource ownership or current state.
412The supplied configuration revision is stale. Read and retry.
422The request body fails the service's strict schema.
428A required If-Match header was not supplied.

Safety model

Defaults designed for automation

No raw provider tokens

Clients receive readiness and bounded actions, never GitHub or Slack credentials.

Explicit access

Every advertised operation declares the authentication level it needs.

Tenant-bound reads and writes

The verified organization identity scopes backing queries and mutations.

Conflict-safe changes

Revision checks protect configuration from accidental lost updates and races.

Human OAuth handoff

Agents may initiate a connection, but a human approves provider authorization.

Stable migration path

The contract begins at app.noxhere.com/api/v1 and can move hosts without changing its shape.

Writes are not automatically retry-safe

Retry reads freely. Retry configuration only after reading the latest revision. Do not retry other writes unless the operation documents idempotency or you can confirm the first attempt failed before processing.

Destructive operations need confirmation

Disconnect, delete, archive, close, and revoke operations are marked destructive. Confirm the target and organization immediately before calling them.

Respect rate limits

On 429, wait for Retry-After when present and add jitter. Never poll setup more often than once every five seconds.

Capture one-time keys

A new Incidents ingest key is returned once. Move it directly into an approved secret manager, never log it, and revoke it if delivery to storage is uncertain.
